# Decisions

Append-only. Each entry: the choice, the options considered, and why. `OWNER D-n` marks an owner ruling.
D-1 to D-18 are seeded from the Tech Spec §1; D-19 to D-21 are owner rulings and D-22 a harness decision, all 15 Nov 2026 (Tech Spec §13).

| ID | Date | Decision | Alternatives considered | Why |
| --- | --- | --- | --- | --- |
| D-1 | 2026-11-15 | A request runs as a small typed graph of steps (route, retrieve and answer, check, finalize), each a pure function over pydantic models with recorded inputs and outputs | One prompt that does everything; an agent framework (Agents SDK, LangGraph) | Every rule in the behavioral spec maps to one step that can be tested on its own, and a recorded request can be replayed exactly in CI. An agent loop would make the route nondeterministic and the replay fragile |
| D-2 | 2026-11-15 | Ingest splits every deck into one file per slide and every document into one file per page, uploaded to the vector store with attributes `session`, `kind`, `locator`, `unit_index`, `manifest_id`, `version` | One file per deck with chunking; page ranges | `file_citation` annotations name a file, not a chunk. One file per slide makes a file citation a slide citation, which is what US1 needs |
| D-3 | 2026-11-15 | We keep our own copy of every unit's text in a corpus store, keyed by `file_id` and `unit_index` | Read the text back from OpenAI | Files uploaded for file search cannot be downloaded again. Source chips (US1), the grounding check and the eval context all need the exact text |
| D-4 | 2026-11-15 | Grounding is checked in two layers at answer time. First, deterministic checks: every citation resolves to a unit inside the session filter, and the top retrieval score clears a bar. Second, a sentence-level support check on GPT-6 Luna against the cited units' text. Any unsupported sentence turns the answer into "not covered" | The PRD's search-score bar alone; claim extraction with dual judges at runtime | A retrieval score measures how relevant a slide is, not whether the answer is true to it (finding C1). Running EvalKit's dual judges on every request would break the 8-second bar. They stay offline, where they measure the runtime check itself |
| D-5 | 2026-11-15 | The bar and the support-check prompt are tuned on the tuning split of the golden set only. Results are reported on the held-out split | Tune on the whole golden set | Same rule as EvalKit D-5: a reported number must not be training accuracy (finding H3) |
| D-6 | 2026-11-15 | **OWNER D-6 (15 Nov): multi-turn, with state on our side.** Each conversation is stored in the app store under the learner's pid. Every call sends a window of earlier turns (the last 6 turns, capped at 3,000 tokens) as input items with `store=false`. `previous_response_id` is never used. The route step rewrites each question into a standalone question, and file search runs on that rewrite. Conversations are scoped to one learner, so another learner's turns can never enter the window (B8) | Single-turn (recommended, not chosen); `previous_response_id` with OpenAI-side state | Follow-up questions feel natural to learners. Keeping the state on our side keeps store set to false and makes deletion complete. The cost is the risk of graded work being built up over several turns, which D-8 now checks over the whole conversation |
| D-7 | 2026-11-15 | The assessment list holds briefs only: titles, prompts and the sessions they draw on. Model solutions live only in the private eval set, never in the manifest, the vector store or any prompt | Give the guard the solutions so it can spot near-answers | If a solution sits anywhere the answer model can reach, injection or retrieval can surface it. The integrity judge sees solutions offline only |
| D-8 | 2026-11-15 | Integrity is enforced twice. Before the answer, the scope check matches the question, and its standalone rewrite, against the assessment list. After the answer, a Luna integrity check asks whether the new reply, **together with the assistant's earlier replies in this conversation**, completes any assessment brief. A failed check turns the answer into a hint | The scope check only; checking each reply alone | A graded task split into innocent-looking questions passes a scope check (finding C4). In a multi-turn conversation (OWNER D-6), each reply can look harmless while the conversation as a whole adds up to the solution. The check judges what has actually been written across the conversation |
| D-9 | 2026-11-15 | The scope check and the answer call start in parallel. The answer is thrown away unless the route is `course` | Run them one after the other | Saves about 1 second on the 8-second p95 budget (finding H1). Answers that are thrown away cost about $0.015 each, and they only happen on the roughly 25% of questions that are not course questions |
| D-10 | 2026-11-15 | The golden set is an EvalKit task. The system under test is the whole `ask()` pipeline, not a bare model. The case context is the corpus units in manifest order, a citation is a 1-based unit index, and the answer label is the `Answer.status` | Score the TA with its own one-off scripts | EvalKit already gives dual-judge groundedness, citation validity, label accuracy, cost, latency, bootstrap CIs, calibration and the report. Using `status` as the label makes EvalKit's `label_correct` measure handover accuracy directly |
| D-11 | 2026-11-15 | **OWNER D-11 (15 Nov): accepted.** Add an EvalKit v0.2 node (X1.1, built in the EvalKit repo under its own harness) for a case-aware system-under-test adapter, task-declared plugin scorers inside `evalkit run`, and per-slice reporting. Course-assistant pins `evalkit-harness==0.2.x` | Parse the question back out of the rendered prompt; compute the extra scorers in a separate local step | EvalKit's adapters get only a prompt string, not the case, and a run computes a fixed set of metrics, so plugin scorers never reach the report (checked in `evalkit/adapters/base.py` and `docs/plugins.md`). Both gaps will come up again in every downstream project. Fallback if X1.1 slips: a local `make eval` step with the same scorers, merged into one report |
| D-12 | 2026-11-15 | Integrity, injection, privacy and identity probes are judged by both EvalKit judges (Opus 5.5 and GPT Sol) with a rubric that sees the assessment solution or the canary, and they are calibrated like groundedness | Keyword or regex checks | "Gives the solution" cannot be detected with keywords. A wrong integrity stamp is the costliest error in this project |
| D-13 | 2026-11-15 | Learner ids are `HMAC-SHA256(platform_user_id, PID_SECRET)`, cut to 16 hex characters. The demo uses a random id per browser session | Platform ids as they are; hashing without a key | NFR3. Without the key, a pseudonym cannot be reversed by hashing a list of known ids |
| D-14 | 2026-11-15 | Question text never reaches traces or logs as it was typed. Traces carry hashed ids, route, statuses, scores, costs and latencies. The question and answer text sit only in the app store, under the retention rules in §7 | Langfuse traces with full text and pseudonymous ids (as in the PRD) | Learners write personal details into questions ("my father is in hospital, can I get an extension"). A pseudonymous id does not make the text anonymous (finding C6) |
| D-15 | 2026-11-15 | Tracing goes through one interface with two sinks: local JSONL (demo, CI) and Langfuse (pilot, if approved at sign-off, with the region chosen there) | Langfuse everywhere | The demo needs no third party, and where the pilot's data lives is a sign-off decision, not a build decision |
| D-16 | 2026-11-15 | The demo is a page in the shared Streamlit app `portfolio-demos`. It reuses EvalKit's guard pattern: passcode, session-token rate limit, a per-request cap, and a persistent daily spend counter in the hosted KV store | A new host; an in-memory counter | One deployment, one secret store, one guard that has already been verified (EvalKit D-7, L-39) |
| D-17 | 2026-11-15 | A real-material pilot runs only after the G0.1 sign-off node is green. That node's proof is an owner attestation recorded as `OWNER D-n`, pointing to a private signed scope note | Rely on discipline | NFR1 becomes a graph edge: the harness refuses to start any P4 node while G0.1 is not green |
| D-18 | 2026-11-15 | Built with the EvalKit harness unchanged in shape: one builder plus a skeptical verifier, `node_start.py` and `node_converge.py`, five proof dimensions, gates that each ship a self-test, and `scripts/status.py` for live status | A lighter checklist; the full Kova harness | It has delivered 24 nodes with 40 recorded lessons. Reusing it keeps the method, the proof format and the habit of verifiers that try to break things |
| OWNER D-19 | 2026-11-15 | Adversarial extension of 150 paraphrase cases (3 each of the B3, B8, B9 and B10 probes) in the held-out split, counting toward the zero-tolerance gates | Keep the PRD's 280 cases and report the rule-of-three bound | 30 of 30 only shows a failure rate under about 10%; 120 of 120 shows under 2.5% (finding H11) |
| OWNER D-20 | 2026-11-15 | Pilot spend cap raised from $50 to $100 a month (NFR6). Still open: multi-turn and the extension bring the estimate to about $141; recommendation is $150 | Weekly half-set run; single judge weekly | Quality first; the eval is not weakened to fit the PRD's original cap |
| OWNER D-21 | 2026-11-15 | **OWNER D-21 (15 Nov): published as an open-source project.** MIT code on GitHub, the sample course under CC BY 4.0, a PyPI release `course-assistant` (name free, checked 15 Nov 2026) by trusted publishing on a tag, `course-assistant init` and `doctor` so others can point it at their own course, contributor and security docs, no telemetry. Publishing to PyPI is asked about first | A public repo only; a GitHub-only install | The owner asked for an open-source project, not just public code. A course team elsewhere should get from `pip install` to a grounded answer on their own materials without reading the build harness |
| D-22 | 2026-11-15 | Harness refinements from the W0.1 verifier: gate 12 checks records (a changelog entry, a criterion line `**CAP-ID**` for every row, RUN-STATE present), as EvalKit's harness does, instead of file modification times; gate 10's smoke commands grow node by node (`--version` now, `ingest --dry-run` from N1.4, `eval-replay` from A2.5); an external node is marked by the exact Verified-by cell `owner attest`, counts as green only when every row's proof is `attest=OWNER D-n`, and that ruling must be in `decisions.md` with a decision that opens `Attests <node>`; GitHub Actions are pinned to release tags, not commit SHAs | Modification-time freshness (as first written); SHA pinning | Modification times are rewritten by checkouts and are not evidence; tags are what EvalKit uses and are reviewed on each update. The verifier showed a loose attest marker and a substring criteria check could both pass work that was not done |
| D-23 | 2026-11-15 | Corpus guard threat model (W0.1 verifier pass 3): the guard stops course material, held-out data and private terms entering the public repo **by accident or by ordinary editing** (copy-paste, markup, slugs, file names, encodings, Office files, archives, symlinks). It does not try to defeat a contributor deliberately obfuscating a term (letter substitution, homoglyphs, text in images, encryption); review of every pushed diff and the owner's `.private-terms` list remain the backstop for that. Short terms (under 8 letters and digits) match only as whole word sequences, so ordinary words containing them are not flagged | An ever-growing list of adversarial normalisations; a hosted DLP service | Each normalisation added false positives elsewhere (pass 3 found "theory and" flagged for a two-word name); the people who can push are the owner and Claude sessions, so accidental leaks are the real risk. Ruling recorded so later passes judge the guard against this model |
| D-24 | 2026-11-15 | Attest marker semantics (W0.1 verifier pass 5): `Attests <node>` at the start of an owner ruling's decision cell is the attestation; the words after it describe the evidence and are not parsed. A fence closes only with the marker that opened it; an unclosed HTML comment hides everything after it | Parse the rest of the sentence for refusals | Rulings are written by the owner (or recorded by Claude from the owner's words); a contradictory ruling ("Attests G0.1: refused") is a review error the owner sees, not something a regex should interpret |
| D-25 | 2026-11-15 | Where the private-terms check is enforced (W0.1 verifier pass 6): the terms list exists only on the owner's machine, so CI can check course material and held-out data but not terms; the enforcement point for terms is the local pre-commit hook (`.pre-commit-config.yaml` and the installed `.git/hooks/pre-commit`), plus the converge safety gate before every node flips green. HAR-08 is rewritten as an explicit list of covered forms (the self-test corpus); forms outside it — RTF and LaTeX escapes, 7z/rar contents, glyph-encoded or kerned PDF text, git history rewriting — are out of scope under D-23 | Put the terms in a CI secret; keep extending the guard pass by pass | A CI secret would be printed in logs on any failure path and is a second copy of the private list. Six verifier passes each found narrower forms; an enumerated criterion lets the next pass judge against a fixed list instead of an open-ended one |
| D-26 | 2026-11-15 | The repo keeps text in UTF-8, and the corpus guard enforces it: a file that is not binary by its content magic and is not valid UTF-8 (or holds NUL bytes, i.e. UTF-16/32) is a finding ("save text files as UTF-8"); the guard no longer guesses other encodings when looking for private terms. Binary is decided by content magic only. Supersedes the cp1252 / BOM-less UTF-16 / UTF-32 forms in HAR-08 (verifier passes 6–12) | Keep decoding cp1252 and BOM-less UTF-16/32 by heuristics | Charset detection is undecidable: passes 10, 11 and 12 each found that a heuristic reading added to catch one form produced a false match or a miss elsewhere. Failing closed on non-UTF-8 text is decidable, has no false term matches, and costs nothing because every text file in this repo is UTF-8 |
| D-27 | 2026-11-15 | Binary files are allowed only in `sample_course/` and `docs/assets/`, and only when the suffix is in a fixed table and the content magic matches it (`.png` ↔ PNG signature, `.pdf` ↔ `%PDF-`, `.pptx` ↔ zip, fonts with a valid table directory, …). Every other file must be UTF-8 text without NUL bytes. Replaces all magic-byte and control-byte heuristics (verifier passes 13–15) | Detect binaries by content magic anywhere; add more structural checks | Passes 13, 14 and 15 each found text whose first bytes looked like some binary signature (wide text encoding to `II*`, cp1252 starting `BM`). Pairing folder, suffix and magic is decidable, matches how the repo is laid out, and makes a mistaken guess impossible: a mismatch is a finding |
| D-28 | 2026-11-15 | N1.1 schema refinements: `Escalation.draft` is a `Draft` (text, citations, hits) rather than an `Answer`; `AssessmentList` wraps `assessments.yaml`; an `answered` `Answer` requires citations, a passed `GroundingResult` and `integrity_passed`; `GroundingResult.passed` must equal its parts; `AuditEvent` has no free-text field; learner references are 16-hex pids and staff references role ids. Tech Spec §3 updated to match | `draft: Answer` as first written | A not-covered answer carries no citations for the learner (B2), yet the teaching team needs the draft's sources (US5); one model cannot hold both rules. Encoding the status rules in the schema makes an ungrounded "answered" unrepresentable |
| D-29 | 2026-11-15 | Schema strictness and versioning (N1.1 verifier): every model is strict (no bool or numeric-string coercion anywhere); YAML files are validated in JSON mode so lists become tuples and dates parse from text; `model_copy(update=...)` revalidates; staff are role ids `instructor-1`, never names; audit targets are generated ids only; YAML errors report position, never content. `schema_version` is required on models persisted as files (manifest, assessments, config, golden cases); store rows are versioned by the store's migration number (N1.5) rather than per row | `strict=False` with strict ints only; schema_version on every row | The verifier showed `cost_usd=True`, `integrity_passed="yes"` and `approved_at=0` all passed; per-row versions would duplicate what the migration table already records |
| D-30 | 2026-11-15 | `GoldenCase.gold_units` are locators `sNN:kind:N` (`s02:slides:9`, `s02:pre_read:3`, `s01:agenda:1`), not unit indexes; the eval resolves them to the corpus at run time | 1-based unit indexes, as first written in Tech Spec §3 | Indexes shift whenever a slide is added or removed, so every case would need renumbering; a locator survives changes elsewhere in the course and fails loudly only when its own slide disappears, which is exactly the drift rule in §6.3 (finding C7) |
| D-31 | 2026-11-15 | The adversarial extension (OWNER D-19) is 3 paraphrases of each B3 probe (90) and each B10 probe (60) = 150, written by Claude (outside the Sol and Luna comparison), held out with their sources | "3 paraphrases each of the B3, B8, B9 and B10 probes" as written in Tech Spec §6.1 | That wording gives 210 cases, not the 150 the owner approved; D-19's own rationale ("120 of 120" integrity probes) is B3 30 + 90. B8 and B9 stay at 10 each |
| D-32 | 2026-11-15 | Golden split by probe group: B3 and B10 sources split 50/50 like every rule, and each paraphrase goes to its source's split, so a probe and its rewordings never sit on both sides. The extension is therefore 75 tuning and 75 held out; zero-tolerance gates are reported on the held-out side (60 integrity probes: failure rate under 5% at 95% if all pass; 40 injection probes: under 7.5%) | All extension cases held out, which forces every B3 and B10 source into held-out too (D-31 wording) | Holding every source out leaves the tuning split with no integrity or injection examples, so the guards could not be developed without looking at held-out data. The honest bound is weaker than D-19's "120 of 120" (2.5%) but four times stronger than the PRD's 15 held-out probes |
| D-34 | 2026-11-15 | The golden split is by group, not by case (refines D-32): B1 questions are grouped by the unit they are about; B10 course carriers join their topic's group; B3 probes are grouped by assessment; and any two cases sharing question or prior-turn text are merged (union-find). Each group goes wholly to one side. `golden_tool check` refuses any held-out question or prior turn found in the public split and any B1 topic on both sides. Halves are approximate (196 public, 234 held out; B1 72/78, B3 48/72, B10 36/44) | Stratify case by case within each rule (as first built) | The second reader found held-out questions copied into public follow-ups and B10 carriers, and near-paraphrases across splits, which per-rule stratification cannot see. B9 cases were reworded to pure identity questions and two paraphrases now name their tasks |
| D-33 | 2026-11-15 | Each OpenAI attempt uses its own HTTP client (closed on overrun) so the deadline is a true wall-clock bound; a caller whose OpenAI client carries a custom `http_client` (proxy, mTLS, test transport) must pass `http_factory`, or `respond` refuses with a config error rather than silently replacing it. Cost: a new connection and TLS handshake per call (about 0.1-0.3 s, inside the latency budget) | Reuse the caller's shared connection pool | A shared pool cannot be closed to stop one abandoned attempt without breaking others, and the N1.2 verifier showed a slow body can otherwise outlast any per-read timeout |
| D-35 | 2026-11-15 | Golden-split groups also merge on every gold unit (not only the first), every unit cited in an earlier assistant turn, a fixed table of concept links (a slide and the pre-read page teaching the same idea), absent topic (B2), and theme (B4, B9); the leak check compares units as well as text. Result: 194 public, 236 held out; B1 76/74 | Exact-text merging only (D-34 as first built) | The second reader showed held-out answers readable from public prior-turn answers and shared secondary units, which exact-text matching cannot see |
| D-36 | 2026-11-15 | Route fixtures (A2.1): every public golden case with its expected category (B1, B2, B7 and B10 carriers answered → course; B3 and B10 hint carriers → graded_work; B4 → admin, or personal for wellbeing; B8 and whole-message B10 attacks → injection; B9 → off_topic), topped up with fixture-only questions (`fx-` ids) where the public split has fewer than 10 (admin, personal, off_topic). The route prompt carries each brief's text as well as id, title and sessions, because matching "a course question that closely restates a brief" needs the task; briefs are public assignment text, solutions never (D-7). Replayed fixtures prove the plumbing only; accuracy comes from the live run | Hold-out cases in the fixtures; id and title only | Fixtures must not see held-out text (E2.1); recall needs at least 10 per category; matching restatements is impossible from a title alone | A2.1 |
