# E2.4 acceptance criteria

All criteria are proved offline: scripted model outputs, fake judges, the public golden split, held-out stand-ins relabelled inside temporary run folders, scratch git repositories; no network. The live gate on real held-out outputs is a prepared command, pending in RUN-STATE.

Before the criteria, E2.3's three should-fix items each have a passing test: a branch that drops a tuning-log line committed on its parent fails the append-only check although the merge-base never had the line; `certified_calibration` reads a copied run folder or a changed rubric (`RUBRIC_HASH`, `JUDGE_PROMPT_HASH`) as uncalibrated; `record_fixture` refuses a case listed in `golden/heldout/MANIFEST.json` even when its meta says tuning, before writing anything, and a failure part-way leaves the tracked fixture folder unchanged.

**GAT-01** `make eval` applies §6.5 and exits 0, 1, 2, 3 or 4. `release.verdict` on a run folder computes every §6.4 gate from EvalKit records (grounded rate with its lower bound, citation validity and locator correctness, handover, zero-tolerance integrity, injection, leak and identity, latency p95), the paired Holm regression against the last live baseline, `judge_mode = dual`, both calibrations certified by `certified_calibration`, the committed regression fixture, the tuning log and the coverage rule, and runs D-54's held-out exposure guard where the private file exists. A passing scripted run exits 0; each planted failure exits 1 and is named; a run that is not exactly the MANIFEST's held-out set (minus drift-retired ids, no duplicate or extra case), whose cases differ from the held-out file that matched the MANIFEST (after drift), or that has a missing score, exits 2, and every input-only check (the cases file, MANIFEST ids, content including context and source, duplicates, records for unknown cases, the baseline's shape and overlap with the run (a baseline given or expected but missing or malformed, naming an unknown metric, lacking a gated one, or sharing fewer than 2 applicable cases for any metric exits 2, so an accepted baseline always compares every gated metric; a first release only with no `--baseline` and no `LIVE.json`), the summary's JSON shape, what the cases alone decide) runs before the cost-cap and pending stops, so it exits 2 whether the run is complete, capped or pending, while completion-dependent checks (a B1 record with citations, missing scores) run after them; every exit of `release_gate.py eval`, including an unparsable command line, writes `gate.json`, and any non-zero `eval_live` exit blocks the flip and merges into the exit code by precedence; a run stopped at the cost cap exits 3; pending judging exits 4; the precedence is 2 > 3 > 4 > 1. `make eval`, `make eval-check` and `make eval-offline` call `scripts/release_gate.py`, whose exit code is the verdict's (0 to 4, also in `gate.json` as `exit_code`); GNU make reports any non-zero recipe as 2, so make itself exits 0 or 2 and CI calls the script directly; duplicate records for a case and a baseline sharing no case with the run exit 2; `gate.json` holds no case text.
**GAT-02** CI job on manifest or rules change; weekly scheduled run; results as artifacts. `.github/workflows/eval-gate.yml` runs on push and pull request touching a manifest, the rules code, the model-call code, `uv.lock`, the tuning log, the golden set or the eval code, weekly on a schedule, and by hand; its offline job uses no secret, runs `release_gate.py offline` and uploads `runs/gate/`; its live job gives each secret only to the steps that need it, checks for the API keys and the held-out bundle and skips every live step when any is absent, and otherwise uploads only `gate.json` and `summary.json`. `release_gate.py offline` passes on the committed repo, fails on a broken fixture or log, and writes its result file.
**GAT-03** Corpus version flips to live only on a pass; removals apply at once. `flip_live` writes `LIVE.json` and the per-case baseline only for an exit-0 verdict on the candidate corpus version and writes nothing otherwise; a candidate that only removes units goes live at once with no gate; `serving_corpus` drops every unit no longer in the ingested corpus from the live view at once, while a candidate that adds units stays unserved until a passing gate; `release_gate.py eval` flips only on exit 0.
**GAT-04** Drift retirement: cases whose gold units are gone are retired or converted; the coverage rule blocks go-live. `drift` keeps cases whose gold units all exist, converts a case whose gold units and whole session are gone into an absent-topic case (B2, `not_covered`), and retires any other case with a missing gold unit; `eval_live` applies it before building cases and records the ids; `coverage_problems` requires 15 B1 cases per corpus session and 3 B3 probes per assessment after drift, and any problem makes the gate exit 1.
