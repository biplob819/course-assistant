# D3.1 acceptance criteria

All criteria are proved offline: A2.5 replays, scripted model outputs through N1.2's `respond`, a file-backed spend counter, an in-memory KV and an injected REST transport; the public golden split only; no network. The live `make demo-cache` run and the demo OpenAI project are owner steps, pending.

**RPL-01** `make demo-cache`: about 20 curated questions, at least two per status. `CURATED` holds 20 public golden ids with at least two per learner-visible status (`answered`, `not_covered`, `hint_only`, `handed_over`) and refuses an id outside the public split; `build_cache` runs each through the real `ask()` with a `Recorder`, stores the Answer its replay gives, leaves out (and names, with no text) any case whose status differs from the expected one, and fails unless two remain per status; `verify_cache` replays every stored case through `ask()` with no API call to the identical Answer with every recording used; `scripts/demo_cache.py` (run by `make demo-cache`) prints the estimate first, refuses without `--yes`, the key or under the cost cap, dry-runs and checks offline, and prints no question or answer text.
**RPL-02** Guard: passcode, session-token rate limit, per-request cap, persistent daily KV counter; one cost number (L-39). `Guard.allow(estimate, session_token)` checks the passkey, the per-request cap, the session rate limit and, on the owner's key, reserves exactly the estimate in a `SpendCounter`; the file-backed and KV counters persist across instances, never let concurrent reservations pass the daily cap, and a store outage refuses readably and gives the rate-limit slot back; `CappedSource` refuses any call whose bound would take the request past its ticket, counts failed and retried attempts at their full bound, and the settled total is what the executor counted, so guard, counter and executor use the ticket's one number; a visitor's own key holds nothing against the daily budget but still meets the cap and rate limit; any exception inside `Assistant._settle` is audited and alerted with no text.
**RPL-03** Separate demo OpenAI project with a hard spend limit. The operator steps are in the spec (separate project, hard monthly limit, project-only key as `OPENAI_API_KEY` in the host secret store); the live demo paths read their key and secrets only from the named secrets (`OPENAI_API_KEY`, `DEMO_PASSKEY_HASH`, `DEMO_KV_REST_URL`, `DEMO_KV_REST_TOKEN`), never from a file in the repo, and the demo cache build refuses without the key; the guard's daily cap must sit under the project's limit.
**RPL-04** Passkey gate on every page and API route: no question is answered without a valid passkey, including for visitors who bring their own OpenAI key; passkeys are stored hashed, can be revoked, and failed attempts are rate-limited. `LiveDemo.ask` and `LiveDemo.replay` call `PasskeyGate.require` before anything else, with or without a visitor key; the passcode is a 6–12 digit code kept only as a salted PBKDF2 hash read from `DEMO_PASSKEY_HASH` at every check and compared in constant time; changing the hash revokes every unlocked session and removing it closes the gate; failed attempts lock the session and the IP after five in fifteen minutes, even for the right code; `course-assistant passkey-hash` reads the code without echo and prints only the hash; no passcode, hash, salt or visitor key reaches a log, error, trace or repr.
